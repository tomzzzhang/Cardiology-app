## Verdict

**Wave 0 is sound and close to its definition of done; do not merge yet.** The scaffold, schema v0
transcription, validator, stub pack, contracts, CI, and Pages workflow are faithful to
`docs/build_plan.md` v1.2, and every local gate passes against the frozen target. I found no
correctness defect in the schema semantics, no privacy or provenance violation, and no breach of the
free-cutter / vetted-wedge boundary. There is one deployed-behavior defect (a browser without WebGL
gets a fully blank page — verified empirically), one meaningful CI coverage gap (the production base
path is never exercised by any automated check), and a set of smaller hardening items. All are
repairable without resolving the three open owner decisions already recorded in the handoff.

## Findings, ordered by priority

### C1 — HIGH. A browser without WebGL renders a completely blank page

`src/viewer/HelloViewer.tsx` constructs `new THREE.WebGLRenderer(...)` inside its effect with no
failure handling. When context creation fails, the constructor throws, React has no error boundary,
and the entire tree unmounts — including the pack-status panel and the "educational, simulated, not
diagnostic" footer.

Evidence (empirical, against the frozen target's production build served by `vite preview`,
Chromium launched with `--disable-webgl --disable-webgl2 --disable-3d-apis`):

```
page errors:            ["Error creating WebGL context."]
#root innerHTML length: 0
document.body.innerText: ""
```

Hospital desktops are a first-class target (`docs/build_plan.md` "Stack", `docs/mvp_scope.md` locked
decision 4), and locked-down hospital machines with GPU acceleration disabled are exactly where a
WebGL context is most likely to be refused. Wave 0's own deliverable is a deploy smoke test; a blank
page with no message fails that smoke test on such machines, silently. The CI visual suite cannot
catch this because the CI runner has software WebGL (SwiftShader).

Smallest repair: catch renderer-construction failure in `HelloViewer`, render a visible fallback
message inside the viewer region, and leave the rest of the shell (pack status, disclaimer) mounted.
Add a focused Playwright test that launches with WebGL disabled and asserts the shell still renders
with the fallback visible. No schema or contract change involved.

### C2 — MEDIUM. No automated check exercises the production base path

The Pages workflow builds with `BASE_PATH=/<repository-name>/`; every CI job builds and tests at
`/`. A regression that hardcodes a root-absolute URL (the exact class of bug the derived-base design
exists to prevent) would pass typecheck, lint, unit tests, and the visual suite, and only fail on the
deployed site after a merge to `main`.

I verified positively that the current code is correct under a non-root base — this is a coverage
gap, not a present bug:

```
BASE_PATH=/Cardiology-app/ npm run build
dist/index.html   → src="/Cardiology-app/assets/index-….js"  (and the css href)
bundle            → …return`/Cardiology-app/packs/…          (packUrl via import.meta.env.BASE_URL)
```

Smallest repair: a CI step that builds with a sentinel base (e.g. `BASE_PATH=/base-path-check/`) and
asserts `dist/index.html` and the emitted bundle reference it (and that the pack URL is prefixed).
That is a grep-level assertion, cheap and deterministic. A fuller variant — running the Playwright
suite against a base-prefixed preview — is heavier and not required to close the gap.

### C3 — MEDIUM. The asset-path traversal invariant is bypassable in URL semantics

`AssetPath` (`src/schema/primitives.ts`) rejects a leading `/`, `://`, and literal `..` path
segments, and `contracts/pack-loader.md` states the loader "rejects absolute URLs and `..`
traversal". But `resolveAsset` resolves with the WHATWG URL parser, under which backslash segments
and percent-encoded dot segments also traverse. Verified against the frozen schema:

```
"..\\outside.gltf"          schema accepts → resolves to <packs root>/outside.gltf
"a\\..\\..\\outside.gltf"   schema accepts → resolves to <packs root>/outside.gltf
"%2e%2e/outside.gltf"       schema accepts → resolves to <packs root>/outside.gltf
"a/%2e%2e/%2e%2e/out.gltf"  schema accepts → resolves to <packs root>/out.gltf
```

Mitigations that hold today: packs are first-party repository content, and the Node-side existence
check in `scripts/validate-packs.ts` treats those strings as literal filenames on Linux, so a shipped
pack using one would fail CI as a missing asset. Severity is therefore low-medium hardening, not an
exploitable defect. The repair — extending the `AssetPath` refinement to also reject `\` and
percent-encoded dot segments, with unit tests — **edits a schema file**, which workers must not do
unilaterally. I recommend it only under the reconciliation's authority that it unambiguously
*enforces* the invariant the schema and contract already state, adding no new semantics. If the
reconciliation does not accept that reading, this defers to a contract-change issue.

### C4 — MEDIUM-LOW. The docs/ guard is stood down for the entire life of the initial-sync PR

`.github/workflows/ci.yml` ("docs/ is read-only for workers") exits clean whenever `docs/` does not
exist on the PR base commit. That correctly admits the initial sync, but the stand-down condition
holds for **every subsequent commit on the same PR** — a later commit on this branch could modify
the already-synced `docs/` and the guard would stay green, because `docs/` still does not exist on
`main`. Protection only arms once this PR merges.

I verified the current history is clean: `git log --follow -- docs/` shows exactly one commit
touching `docs/` (`c0aa8a3`, the initial sync) between branch creation and the target SHA.

Smallest repair: in the stand-down branch, additionally fail if any commit in the PR range shows a
**modification** (not addition) to `docs/` — e.g. `git log --diff-filter=M "$base"..HEAD -- docs/`
non-empty fails. The initial add passes; any post-sync edit inside the same PR fails. Mechanical, no
owner decision.

### C5 — LOW. `pages.yml` can be manually dispatched on a non-default branch

`pages.yml` triggers on `push: [main]` and `workflow_dispatch`. Once the workflow file exists on
`main`, `workflow_dispatch` can be pointed at any branch, and the build job would build and upload
that branch for deployment. GitHub's auto-created `github-pages` environment normally restricts
deployment branches to the default branch, which would make the deploy job fail — but that
protection is repository state, not repository code, and I could not verify it from this session.
The spec (`docs/build_plan.md` "Repo and hosting") says Pages deploys from `main`.

Smallest repair: gate the deploy job (or both jobs) on the default branch ref while keeping
`workflow_dispatch` useful for manual redeploys of `main`. One `if:` line; enforces the documented
behavior regardless of environment settings.

### C6 — LOW. A red `main` does not block a Pages deploy

`pages.yml` re-runs pack validation and provenance before publishing (good), but does not run — or
wait for — typecheck, lint, unit, or visual jobs; `ci.yml` runs them on push to `main` concurrently
with the deploy. A commit that merged with a green PR but regresses on `main` (e.g. via a
merge-skew interaction) would still publish. Residual risk is small given serialized owner-controlled
merges; recording it so the owner can accept it deliberately or ask for a `workflow_run` dependency
later.

### C7 — LOW. Pack-loader failure paths have no unit coverage

`loadPack`'s error paths — network failure, HTTP error, invalid JSON, wrong `schema_version`,
schema-invalid pack — are all correct (I exercised each with a stubbed `fetch` against the frozen
tree; every one produced the intended `PackLoadError` with the intended message, including the
version fast-path message for a `"1"` pack), and the App surfaces the message in a visible error
panel. But nothing in the repository executes these paths: unit tests cover only the schema, and the
visual suite covers only the happy path. The behavior that makes a bad pack "fail loudly at the
boundary" (contract rule 4) is unlocked against regression. Smallest repair: a loader unit-test file
with a stubbed `fetch` covering those five paths plus `packUrl`/`resolveAsset` behavior.

### C8 — INFORMATIONAL, grouped smaller observations (no repair required this round)

- **Guardrail pattern edges.** The committed-absolute-path patterns require a trailing separator
  after the username segment, so a bare home path without one escapes the net; the placeholder check
  in `check-provenance.ts` is exact-match (`"tbd"` trips it; `"tbd - fill in"` does not). Both look
  deliberate (avoiding false positives); noting so the limits are on record.
- **Asset existence checks do not walk glTF internals.** `validate-packs.ts` checks the two directly
  referenced assets; a future pack whose glTF references an external `.bin`/texture would not have
  that file's existence checked. The stub embeds its buffer as a data URI, so wave 0 is unaffected;
  belongs to the wave 1 model-pipeline tooling.
- **`discoverPacks` throws on a pack directory missing `pack.json`** instead of reporting it as a
  collected failure line — a crash-with-stacktrace instead of a clean CI message. Cosmetic.
- **`readSchemaVersion` fast-paths only string versions.** A pack declaring numeric `0` falls
  through to the full shape-error wall rather than the friendly version message. Defensible reading
  of "declares anything else"; cosmetic.
- **The hello viewer renders continuously when not frozen** (rAF loop, no on-demand rendering) and
  handles no `webglcontextlost` event. Acceptable for a wave 0 smoke test; both belong to viewer-core
  (wave 1c) where the real renderer lands.
- **`npm run verify` does not include `npm run build`** — CI's quality job runs the build as its own
  step, so the gap is only in the local-gate name. Worth remembering when quoting "verify green" as
  evidence.

## Smallest recommended repair set

1. **C1** — WebGL-unavailable fallback in `HelloViewer` + Playwright test with WebGL disabled.
2. **C2** — CI production-base step: build with a sentinel `BASE_PATH`, assert the emitted
   `dist/index.html` and bundle are base-prefixed.
3. **C7** — loader failure-path unit tests (stubbed `fetch`; five paths + URL helpers).
4. **C4** — docs/ guard: inside the stand-down branch, fail on any `--diff-filter=M` commit against
   `docs/` in the PR range.
5. **C5** — default-branch guard on the Pages deploy path, keeping manual redeploy of `main`.
6. **C3** — `AssetPath` hardening (reject `\` and percent-encoded dot segments) + unit tests —
   **only if** the reconciliation accepts it as unambiguous enforcement of the stated invariant;
   otherwise defer via a contract-change issue.

Explicitly *not* recommended this round: schema semantic changes of any kind beyond C3's
enforcement reading, visual-baseline commits (wave 1, per the documented seeding plan), `webglcontextlost`
handling and render-on-demand (viewer-core, wave 1c), glTF-internal asset walking (wave 1a tooling).
